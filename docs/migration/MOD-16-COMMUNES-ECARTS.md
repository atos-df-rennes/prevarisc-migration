# MOD-16 — Gestion des communes — Rapport d'écarts

## Synthèse

| Indicateur | Valeur |
|---|---:|
| Règles de gestion analysées | 19 |
| Écarts confirmés | 7 |
| Points à vérifier | 5 |
| Niveau de risque | Élevé |
| Niveau de confiance | Bon |

### Constats clés

- Le périmètre de consultation reste globalement aligné : liste alphabétique, chargement AJAX de la fiche détaillée, affichage du code INSEE et du code postal en lecture seule.
- Le périmètre de **fusion de communes** est en revanche partiellement migré seulement : le transfert des adresses et des rues existe, mais deux suppressions métier du legacy ont disparu.
- Les deux écarts les plus critiques sont l'absence de **suppression des liaisons groupement–commune** et l'absence de **suppression des règles de commission** lors d'une fusion.
- La logique d'arrêt global du traitement n'est plus respectée : Symfony continue sur la fusion suivante alors que la spec et le legacy imposent l'arrêt du lot.
- La sauvegarde des coordonnées de mairie n'est plus asynchrone et la fonction « Mairie » n'est pas initialisée explicitement lors de la création d'une nouvelle fiche.

## Recommandations

1. ✅ **[RÉSOLU le 2026-07-03] Compléter la fusion Symfony** avec la suppression des liaisons groupement–commune (E-01) avant la suppression des communes absorbées. Implémenté via `FusionDesCommunes::deleteGroupementCommuneLiaisons()`, testé unitairement dans `tests/Service/FusionDesCommunesTest.php`.
2. ✅ **[RÉSOLU le 2026-07-03] Supprimer les règles de commission liées aux communes absorbées** (E-02). Implémenté via `FusionDesCommunes::deleteCommissionRegles()`, qui supprime explicitement les entités `CommissionRegle` via Doctrine (évitant les lignes orphelines dans les tables de jointure sans contrainte de clé étrangère). Testé unitairement dans `tests/Service/FusionDesCommunesTest.php`.
3. ✅ **[VALIDÉ le 2026-07-03] Arrêt global sur erreur de cohérence (E-03)** : Le comportement Symfony (traitement partiel avec erreurs loggées) est une amélioration justifiée par rapport au legacy (arrêt global). Conforme au retour utilisateur qui estime que plusieurs fusions dans le JSON ne doivent pas être bloquées par l'échec d'une seule. Aucune action requise.
4. ✅ **[RÉSOLU le 2026-07-03] Améliorer l'UX de sauvegarde commune** (E-04). Le formulaire est chargé en AJAX dans la page principale (avec un select de communes). Après POST de sauvegarde, redirection vers `admin_communes?id=X` avec l'ID en paramètre. Le template reçoit cet ID et ajoute l'attribut `selected` directement dans l'option HTML (sélection native, sans JS superflu). Le JavaScript existant détecte le changement du select et recharge les informations via GET AJAX. Aucun rechargement complet de page ; le message Flash s'affiche au retour à la liste. Implémenté dans `CommunesController::index()` (récupère `selectedId`) et `CommunesController::informations()` (redirige avec ID). Template `communes/index.html.twig` utilise `selected` sur l'option.
5. ✅ **[RÉSOLU le 2026-07-03] Initialiser explicitement la fonction "Mairie" dans la fiche de coordonnées** (E-05). Implémenté en une ligne dans `CommunesController::informations()` : avant la création du formulaire, le setter `utilisateurInformations->setFonction()` reçoit la constante `Fonction::MAIRE` (ID=2) si le champ est vide. Le formulaire n'expose aucun champ `fonction` puisque cette propriété est gérée entièrement côté serveur. Ultra-minimaliste, aucune complexité. Tests complets (634 tests) verts, PHPStan niveau 10 sans erreur.
6. **Ajouter une vraie validation sur l'upload de fusion** (JSON uniquement, un seul fichier).
7. **Décider du niveau de sévérité attendu** pour les répertoires / incohérences / imports : si l'objectif est l'iso-fonctionnalité stricte, les comportements de blocage et les messages mixtes doivent être réalignés.
